# M2: Activity-Matched Generator

## 1. Task

Design and evaluate a generator for synthetic anomaly edges. It should generate the required `1%`, `5%`, or `10%` of the original events while matching the recent activity of normal reference edges. Parameters are selected without using the final test set.

## 2. Evaluation

- **Feasibility:** generate the full target count; report failures and check for self-loops, repeated pairs, prior pairs, and same-time normal pairs.
- **Activity matching:** use the last `N` historical events before the injection time. For reference edge `(u,v)` and generated edge `(x,y)`, measure

  `0.5 * (|log(1+a_u)-log(1+a_x)| + |log(1+a_v)-log(1+a_y)|)`

  Lower is better. Report mean, median, and quantiles.
- **Efficiency:** report generation time. Runtime and theoretical complexity should be reported separately.

## 3. Generator 1: Activity-Quantile Matching

Implementation: [`src/generators/activity_matched.py`](src/generators/activity_matched.py); injection flow: [`src/injection.py`](src/injection.py).

The generator uses `N=100` previous events and `Q=10` activity-rank bins. For each anomaly, it randomly selects a normal edge at the same timestamp as the reference, samples each endpoint from the corresponding activity bin, and rejects invalid pairs. Same-time events enter history only after the timestamp batch is generated.

| Rate | Target / generated | Mean error: matched / random | Median error: matched / random | Time (s) |
|---:|---:|---:|---:|---:|
| 1% | 597 / 597 | 0.6431 / 1.2901 | 0.4581 / 1.2425 | 1.158 |
| 5% | 2,989 / 2,989 | 0.6462 / 1.3009 | 0.5058 / 1.2425 | 5.121 |
| 10% | 5,979 / 5,979 | 0.6478 / 1.2844 | 0.4904 / 1.1989 | 11.091 |

All runs completed with zero recorded constraint violations. These are single-seed results on the 59,795-event UCI Messages data.

### Complexity

Let `E` be the original event count, `p` the injection rate, `M=floor(pE)` the anomaly count, `N` the window length, `V` the number of historically observed nodes, and `L` the size of an activity-bin candidate pool. The current implementation also sorts historically observed nodes with activity zero in the current window. A useful upper bound is:

`O(E + M(N + V log V + L^2))`

`L^2` is the low-coverage fallback that enumerates pairs from two candidate bins; it is not `N/Q`. If candidates were restricted to nodes appearing in the current window, then `V <= 2N` and `V log V` could be approximated by `N log N`, but that would change the generator definition.

## 4. Generator 2: Rank-Window Candidate Pool

Implementation: [`src/generators/activity_nearby.py`](src/generators/activity_nearby.py), function `generate_rank_pool_anomalies`.

Let `A=floor(pE)` and `R=floor(A/10)`. For each of `R` sampled reference edges, take `L=10` nodes around each endpoint's activity rank, enumerate up to `L^2=100` point pairs, filter invalid pairs, and rank the candidates by activity error. Select the lowest-error `A` unique pairs.

| Rate | Target `A` | References `R` | Legal candidates | Selected | Mean / median / p90 error | Time (s) |
|---:|---:|---:|---:|---:|---:|---:|
| 1% | 597 | 59 | 5,241 | 597 | 0 / 0 / 0 | 0.397 |
| 5% | 2,989 | 298 | 26,171 | 2,989 | 0 / 0 / 0 | 0.704 |
| 10% | 5,979 | 597 | 51,889 | 5,979 | 0 / 0 / 0 | 0.862 |

Generator 2 completed all three rates and had lower preliminary activity error and runtime than Generator 1. However, its current batch implementation uses benign history only and globally ranks candidates, so its timestamp distribution and history policy differ from Generator 1. It should be protocol-aligned before the final M4 comparison.

For `C` legal candidates, its complexity is approximately:

`O(E + R(V log V + L^2) + C log C)`
