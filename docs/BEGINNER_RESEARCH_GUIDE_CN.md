# 初学者研究导读：为什么“异常检测分数很高”不一定代表模型真的聪明

## 1. 先用一句话说明这个项目

我们研究的是：**如果用人工制造的异常来训练和测试模型，异常制造得太简单，会不会让模型得到虚高的成绩？**

项目使用人与人之间的消息记录。我们把每个人看成一个点，把一次消息交互看成连接两个点的一条边，然后训练模型判断一条边是正常交互还是异常交互。

我们的重点不是发明一个更复杂的分类器，而是设计一种**更公平、更难作弊、可以重复检查的实验方法**。

## 2. 阅读前只需要理解四个概念

### 2.1 什么是图（graph）

这里的“图”不是图片，而是一种表示关系的数据结构：

- 人或账号叫作**节点（node）**；
- 两个人之间的一次交互叫作**边（edge）**；
- 交互发生的时间叫作**时间戳（timestamp）**。

例如，Alice 在 10:00 给 Bob 发了一条消息，可以表示成一条带时间的边：

```text
Alice ----10:00---- Bob
```

很多条这样的记录放在一起，就形成了一个随时间变化的网络，也叫**时间图（temporal graph）**。

### 2.2 什么是异常检测

异常检测就是找出“不像平常行为”的记录。例如：

- 两个从未联系过的账号突然发生交互；
- 一个平时很少活动的账号突然大量联系其他人；
- 某种连接方式与过去的交互规律明显不同。

### 2.3 什么是人工异常

真实数据通常没有足够可靠的“异常”标签，所以研究人员会在正常数据中人工加入一些异常边，再检查模型能否把它们找出来。

这很像老师自己出题，然后让学生做题。问题是：**如果老师出的假题和真题差别太明显，学生可能只学会识别出题痕迹，而没有学会真正的知识。**

### 2.4 什么是特征

模型不能直接理解“这条边很奇怪”，所以我们需要把历史行为变成数字，这些数字叫作**特征（feature）**。

例如：

- Alice 最近联系过多少人；
- Bob 最近发送过多少次消息；
- Alice 和 Bob 过去是否联系过；
- 最近的网络一共有多少节点和连接。

## 3. 文章和项目的研究动机

本项目从 TGF 方法使用的时间图统计特征和 Random Forest 基线出发。传统实验常用一种简单方式生成异常：随机选择两个过去没有连接过的节点，把它们连起来。

这种方法很方便，但可能带来一个严重问题。

假设正常消息通常发生在活跃用户之间，而随机生成器经常选到两个很少活动的用户。此时，模型可能只需要学会下面这条简单规则：

> “如果两端都不活跃，就判断为异常。”

模型的测试分数可能很高，但它没有真正理解复杂的异常行为，只是识别出了随机生成器留下的“指纹”。真实世界中的异常者完全可能非常活跃，因此这种模型不一定能应对真实情况。

这类问题叫作**合成异常评估偏差（synthetic anomaly evaluation bias）**。通俗地说，就是“模拟题太简单，导致考试成绩看起来比真实能力更好”。

### 3.1 请区分“原始方法”和“我们的研究”

这两部分很容易混淆：

- **TGF 原始方法/代码**提供了从历史时间图提取统计特征、再用分类器识别异常的基线思路；
- **我们的课程研究**并不是重新发明 Random Forest，而是检查异常生成方式是否让这个基线得到虚高成绩，并设计 activity-matched 异常、严格实验协议和特征消融来验证这个问题。

所以，我们的主要创新点在**实验问题、异常生成和评估方法**，而不是提出一种新的深度学习网络。

## 4. 我们面对的主要问题

### 问题一：真实异常标签不足

我们需要人工生成异常，但人工生成方式本身可能改变实验难度。

### 问题二：随机异常可能留下明显捷径

随机异常与正常边的端点活跃度差别很大，模型可能依赖这个捷径，而不是学习更一般的交互规律。

### 问题三：训练和测试来自同一个简单生成器

如果训练集和测试集都由相同的随机规则产生，模型只要记住该生成器的特点就能取得高分。这样的实验不能充分说明模型能够泛化到其他类型的异常。

### 问题四：时间数据容易发生信息泄漏

判断 10:00 的事件时，只能查看 10:00 之前的历史。如果把当前事件、同一时间的其他事件或未来事件放进特征，就相当于提前偷看答案。

### 问题五：只看最终分数，不知道模型学到了什么

即使性能下降了，我们仍然需要回答：下降主要来自端点活跃度、两人过去的交互历史，还是整个网络的统计信息？

## 5. 原始检测方法怎样工作

### 5.1 查看多个长度的历史

对于一条待判断的边 `(u, v)`，程序只查看它之前的交互，并分别使用最近 5、50、100、1,000、10,000 和 15,000 条历史事件。

短窗口反映最近发生了什么，长窗口反映比较稳定的长期行为。

### 5.2 为每条边制作“历史体检表”

我们把特征分成三组：

1. **端点活跃度（endpoint activity）**：两端最近联系过多少人、发生过多少次交互，以及它们在所有节点中有多活跃。
2. **节点对历史（pair history）**：这两个节点过去是否联系过、联系过多少次。
3. **全局图统计（global graph）**：历史窗口内有多少节点、多少连接，以及度数和交互次数的整体分布。

只使用 1,000 条历史的 `H1000` 有 34 个特征；合并六个历史窗口的 `combined-H` 有 204 个特征。

需要特别注意：当前的 `global graph` 组并不包含 common-neighbor 或 Jaccard 等邻居重叠特征，所以不能把它直接称为 neighborhood 特征。

### 5.3 用 Random Forest 做判断

Random Forest 可以理解为让 100 棵决策树共同投票。每棵树会学习一些类似的问题：

- 两端是不是很少活动？
- 这两个节点以前有没有联系过？
- 当前网络是否比平时稀疏？

最终综合这些树的判断，得到一条边是异常的分数。

## 6. 我们提出的方法

### 6.1 活动匹配异常生成器

为了减少“端点不活跃”这个过于明显的提示，我们设计了 **activity-matched generator（活动匹配异常生成器）**。

它的基本步骤是：

1. 在一个注入时间找到一条正常参考边；
2. 查看参考边两端在过去 1,000 条事件中的活跃度；
3. 按活跃度把历史节点分成 10 个等级；
4. 从相近活跃度等级中选择两个节点组成异常边；
5. 确保它不是自连接、不是过去已经出现的边，也不与同一时间的其他边重复；
6. 如果找不到合法候选就明确失败，不能偷偷退化成普通随机生成。

可以把它理解成：

- 普通随机生成器可能让“两位几乎从不说话的人”突然联系；
- 活动匹配生成器尽量让“两位活跃程度与正常用户相似的人”形成一条新连接。

这样生成的异常更难仅靠活跃度识别。

### 6.2 更严格的实验协议

为了让比较公平，我们还固定了以下规则：

- 先按时间把正常数据分成 train、validation 和 test；
- 两种异常生成器使用相同的注入时间；
- 两种生成器遵守相同的候选边限制；
- 特征只能使用当前时间之前的历史；
- 模型参数和判断阈值只能使用 train/validation 决定；
- test 只用于最后评估，不能反过来帮助选择参数；
- 使用三个随机种子和三种异常比例，检查结果是否稳定。

### 6.3 三种训练—测试实验

我们设计了三个核心场景：

| 场景 | 含义 | 想回答的问题 |
|---|---|---|
| R→R | 随机异常训练，随机异常测试 | 在传统简单测试中能得到多高成绩？ |
| R→M | 随机异常训练，活动匹配异常测试 | 模型离开原生成器后还能不能工作？ |
| M→M | 活动匹配异常训练，活动匹配异常测试 | 使用更合适的训练数据后能恢复多少？ |

整个研究流程可以概括为：

```text
正常消息记录
    ↓
生成随机异常 / 活动匹配异常
    ↓
严格按过去历史提取图特征
    ↓
训练 Random Forest
    ↓
比较 R→R、R→M、M→M
    ↓
删除或打乱特征组，解释模型依赖什么
```

### 6.4 M5：解释模型为什么变化

M5 使用两种互补方法：

- **重新训练消融（retrained ablation）**：删除一整组特征，再从头训练模型，观察剩余特征能否补偿。
- **分组置换重要性（grouped permutation importance）**：保持模型不变，把某一组特征的测试值打乱，观察模型性能下降多少。

第一种方法回答“没有这组信息，重新学习后还能做多好”；第二种方法回答“当前模型现在有多依赖这组信息”。两者含义不同，结果不必完全相同。

## 7. 我们目前完成了哪些 research

### M1：复现基线

我们复现了 TGF 风格的特征提取和 Random Forest 异常检测流程，确认项目有一个可比较的起点。

### M2：控制异常生成方式

我们实现并冻结了 random 和 activity-matched 两种异常生成器，统一时间戳、候选规则和历史使用方式。活动匹配把平均 activity error 从随机异常的大约 `1.90–2.10` 降到了大约 `0.62–0.67`，说明端点活跃度差距确实缩小了。

### M4：比较跨生成器泛化

实验覆盖 1%、5%、10% 三种注入率、随机种子 42–44、两套特征和三个训练—测试场景。

以 5% 注入率和 combined-H 为例，Final M5 当前环境重新训练得到：

| 场景 | AP（越高越好） |
|---|---:|
| R→R | 0.6999 |
| R→M | 0.2832 |
| M→M | 0.5567 |

R→M 明显低于 R→R，说明在随机异常上学到的模型不能很好地直接识别活动匹配异常。M→M 又明显高于 R→M，说明使用更接近测试异常的训练数据可以恢复不少性能，但还没有完全回到 R→R。

### M5：研究模型依赖哪些特征

正式 M5 包含 216 条重新训练消融结果和 810 次分组置换测量。以同一个 5% / combined-H 配置为例：

- R→R 删除 endpoint activity 后，AP 平均下降 `0.4980`；
- R→M 删除 endpoint activity 后下降 `0.0804`；
- R→M 删除 pair history 后下降 `0.1501`；
- M→M 删除 endpoint activity 和 pair history 后，分别下降 `0.3615` 和 `0.3683`；
- global graph 的影响大多接近零，有时为负，不是稳定的主要信号。

这些结果支持下面的解释：

1. 随机异常实验中的高分很大一部分来自端点活跃度捷径；
2. 活动匹配削弱了这条捷径；
3. 面对活动匹配异常时，两节点过去的交互历史变得更重要；
4. 用 matched 数据重新训练后，模型会同时利用端点活跃度和 pair history。

## 8. 目前还没有完成什么

M3 的完整 generator diagnostics 还没有冻结。我们仍需直接比较正常边、随机异常和活动匹配异常的：

- 度数和活动量分布；
- 邻居重叠或结构接近程度；
- 过去重复交互的残余差异；
- 时间上的集中或突发程度（burstiness）；
- 以上差异在不同注入率和随机种子下是否稳定。

因此，目前可以说“模型对某组特征的依赖发生了变化”，但不能仅凭 M5 就断言“某个具体生成机制导致了全部性能下降”。M5 提供的是模型侧关联证据，不是完整的因果证明。

## 9. 这项研究真正想说明什么

最重要的结论不是“某一个模型最好”，而是：

> 评估异常检测模型时，测试异常是怎样制造出来的，会直接影响我们看到的模型能力。

一个模型在简单人工异常上得分很高，可能只是因为人工异常带有明显痕迹。更可信的研究应当控制异常生成方式、避免时间泄漏、测试跨生成器泛化，并解释模型依赖的特征。

## 10. 初学者常见疑问

### AP 和 ROC-AUC 是什么

它们都是评价排序质量的指标，通常越高越好。异常样本很少时，AP 更直接关注模型能否把少数异常排在前面，因此本项目特别重视 AP。

### 为什么不只看 accuracy

如果 99% 的数据都是正常边，模型把所有边都预测为正常，也能得到 99% accuracy，但它一个异常都找不到。因此 accuracy 在类别极不平衡时容易误导。

### 为什么要使用 validation

validation 像正式考试前的模拟卷，用于选择参数和判断阈值；test 像最终考试，只能最后使用。如果反复根据 test 修改方法，test 就不再公平。

### 为什么多运行几个随机种子

模型训练和异常生成含有随机选择。只运行一次可能碰巧特别好或特别差。多个随机种子可以初步判断主要结论是否稳定，但三个种子仍不能代替更多数据集上的验证。

### 这个项目已经能代表真实异常吗

还不能。当前结论只适用于 UCI Messages、当前 TGF 风格特征、Random Forest 和人工生成异常。真实世界异常更加复杂，最终仍需要带可靠标签的真实数据或更多数据集验证。
